# 模型监控与应用监控对比

## 背景与目的

百炼平台提供了两套互补的可观测性方案：[[model-monitoring]]（模型监控）和 [[application-monitoring]]（应用观测）。前者聚焦于**模型调用层面**的用量、性能与成本管理，后者聚焦于**应用调用链路**的端到端追踪与调试。开发者在生产环境中往往需要同时使用两者，但在不同阶段和场景下侧重点有所不同。本文从多个关键维度对两者进行对比分析，帮助开发者做出合理的技术选型与组合决策。

## 关键维度对比

| 维度 | 模型监控 | 应用监控 |
|------|---------|---------|
| **监控粒度** | 模型调用级（按模型 + [[workspace]] 维度） | 应用调用链路级（按 Span 节点维度） |
| **核心定位** | 用量统计、成本控制、性能基线、异常告警 | 调用链路追踪、节点级延时分析、调试排障 |
| **数据延迟** | 用量统计约 1 小时；高级监控分钟级 | 分钟级 |
| **支持对象** | 平台所有模型（含调优模型）；高级监控限北京/新加坡/弗吉尼亚 | [[agent-application]]、[[workflow-application]]、[[rich-code-application]] |
| **核心指标** | 调用次数、Token 消耗、RPM/TPM、首 Token 延时、失败率、限流错误 | 调用次数、失败率、Token 总量、平均首 Token 耗时、平均调用时长、节点级延时 |
| **输入/输出查看** | 通过模型日志查看单次调用的输入/输出/Token 明细 | 通过 Span 详情查看每个节点的输入/输出及嵌套关系 |
| **告警能力** | ✅ 支持（电话/短信/邮件/钉钉/企微/Webhook） | ❌ 暂不支持 |
| **外部系统集成** | 支持 Prometheus HTTP API，可接入 Grafana | 基于 [[opentelemetry]] 服务存储，暂无对外 API |
| **数据导出** | 通过 Prometheus API 查询或账单导出 | 支持 JSONL / EXCEL 格式导出 |
| **数据标注** | ❌ 不支持 | ✅ 支持布尔值/分类/数字/文本标签，可关联 [[application-evaluation]] |
| **数据保留** | 用量统计仅保留 30 天；更早需通过费用中心查询 | 最长可查看 30 天数据 |
| **计费方式** | 功能免费；模型调用按模型计费标准收费 | 功能免费；Trace 数据存储在 OpenTelemetry 服务中需支付存储费用 |
| **开通方式** | 高级监控/日志需主账号在控制台手动开通 | 需授权 OpenTelemetry 服务角色、开通服务并初始化 LogStore |
| **筛选能力** | 按 [[api-key]]、推理类型（[[real-time-inference]] / [[batch-inference]]）、时间范围 | 按状态、Span Name、输入/输出关键词、延时、Token 量、标签 |

## 功能覆盖范围对比

| 能力 | 模型监控 | 应用监控 |
|------|:-------:|:-------:|
| Token 消耗统计 | ✅ | ✅（应用维度） |
| 模型性能基线（RPM/TPM） | ✅ | ❌ |
| 调用链路可视化 | ❌ | ✅ |
| 节点级耗时分析 | ❌ | ✅ |
| 检索/重排/Embedding 追踪 | ❌ | ✅ |
| 主动告警通知 | ✅ | ❌ |
| Grafana 仪表盘接入 | ✅ | ❌ |
| 免费额度管理 | ✅ | ❌ |
| 评测集联动 | ❌ | ✅ |
| 思考过程查看 | 通过日志查看 | 通过 LLM Span 查看 |

## 适用场景建议

### 优先使用模型监控的场景

- **成本管控**：需要追踪各模型的 Token 消耗趋势，设置免费额度用完即停策略，避免意外费用。
- **容量规划**：通过 RPM/TPM 指标评估模型负载，规划限流阈值和扩容策略。
- **异常告警**：需要在模型调用失败率突增、限流频繁或 Token 消耗异常时第一时间收到通知。
- **多系统集成**：需要将监控数据接入 Grafana 或自建运维平台，进行统一可视化。
- **批量推理监控**：使用 [[batch-inference]] 时需按推理类型筛选和统计用量。

### 优先使用应用监控的场景

- **调用链路调试**：应用包含多个节点（检索、重排、模型推理、插件调用等），需定位具体哪个环节出现延时瓶颈或错误。
- **RAG 应用优化**：需要观察 RETRIEVER、RERANKER、EMBEDDING 等节点的执行效果，优化检索质量。
- **工作流调试**：[[workflow-application]] 中包含条件分支、脚本、函数计算等复杂节点，需要逐节点排查执行逻辑。
- **评测样本构建**：需要从真实线上调用中筛选典型 Case 添加到评测集，持续迭代应用质量。
- **内容审查与标注**：需要对模型输出进行人工标注和分类管理。

### 推荐组合使用的场景

在生产环境中，建议**同时启用两者**：

1. 使用 **模型监控** 建立全局性能基线和成本看板，配置告警规则实现被动防御。
2. 使用 **应用观测** 进行主动的链路分析和问题定位，形成"发现异常 → 定位根因"的完整排障闭环。
3. 结合 [[deep-thinking]] 的思考过程查看能力，在两个维度分别验证模型推理质量。

## 选型决策流程

```
你的核心需求是什么？
├─ 控制成本、监控用量 → 模型监控
├─ 设置告警、对接 Grafana → 模型监控
├─ 排查应用内部节点问题 → 应用监控
├─ 构建评测集、标注数据 → 应用监控
└─ 全面生产运维 → 两者组合使用
```
