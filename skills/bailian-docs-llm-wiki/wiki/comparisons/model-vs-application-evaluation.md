# 模型评估与应用评估对比

## 概述

阿里云百炼平台提供了两套独立的评估体系：**模型评测**和**应用评测**。两者虽然都旨在帮助开发者量化 AI 系统的输出质量，但面向的对象、评估粒度和使用场景存在显著差异。本文从多个关键维度对两者进行系统对比，帮助开发者根据自身需求选择合适的评估方案或制定组合策略。

## 核心维度对比

| 维度 | 模型评测 | 应用评测 |
|------|---------|---------|
| **评估对象** | 单个或多个大语言模型本身 | 智能体应用、工作流应用（含 Prompt、知识库、插件等完整链路） |
| **核心目标** | 模型选型、调优验证、安全风险检测 | 应用输出质量跟踪、上线前后效果对比、持续优化闭环 |
| **评估粒度** | 模型推理能力（语言理解、生成、推理等基础能力） | 端到端应用效果（含检索、重排、工具调用等全链路） |
| **支持的评估模式** | 自定义评测（人工/自动）、基线评测 | 自动评测（旧版）、手动评测（旧版）、评测任务（新版，含评估器 + 标签） |
| **评测目标范围** | 通义千问系列（商业版/开源版）、通义法睿、第三方文本生成模型及其微调版本 | 已发布的智能体应用、工作流应用 |
| **评分输出** | Pass/Fail（分类型）、数值评分（数值型）、相似度分数（0-1） | 1-5 分（旧版自动）、较差/一般/较好（旧版手动）、自定义评分范围 + Pass/Fail（新版评估器） |
| **评测集格式** | 平台评测数据集或推理结果集 | 旧版：`.xls`/`.xlsx`/`.jsonl`；新版：按应用出入参定义表结构 |
| **裁判/评估模型** | 任选推理能力强的模型（推荐通义千问3-Max） | 旧版仅支持 `qwen-max` / `qwen-plus`；新版 LLM 评估器可自定义 |
| **人工评估支持** | 评分员按维度手动打标签 | 旧版逐条打标；新版支持分类/布尔值/数字/文本四种标签类型 |
| **自动评估维度** | 大模型评估（分类型/数值型）、规则评估（字符串匹配/文本相似度） | 旧版基于知识库归因评分；新版支持 LLM 评估器 + Code 评估器 |
| **基线/回归测试** | 支持（C-Eval / CMMLU 等预置基线评测集） | 不直接支持预置基线，需自建评测集进行回归 |
| **归因分析** | 不支持（仅输出评分结果） | 旧版自动评测支持归因（模型理解有误、重排不佳、检索无效等） |
| **横向对比** | 多模型并行评测 | 旧版支持最多 8 个应用横向评测 |
| **可用地域** | 仅中国大陆版（北京地域） | 随百炼平台通用可用区 |
| **计费方式** | 评测过程中模型推理产生的 Token 正常计费 | Token 调用正常计费；新版评估模型限时免费（以公告为准）；独占资源部署模型不额外收费 |
| **前置依赖** | 模型已部署（如微调模型需先完成部署） | 应用已发布；旧版自动评测需配置知识库并开通应用观测 |

## 评估维度能力对比

| 能力 | 模型评测 | 应用评测（新版） |
|------|---------|----------------|
| 文本相似度（ROUGE-L / BLEU / Cosine / Fuzzy Match） | ✅ 内置支持 | ✅ 预置评估器模板 |
| 字符串精确匹配 | ✅ 规则评估 | ✅ Code 评估器 |
| 语义理解评分（如相关性、幻觉检测） | ✅ 大模型评估维度 | ✅ LLM 评估器 |
| 自定义 Python 脚本评分 | ❌ | ✅ Code 评估器（Python 3.10） |
| 预置基线榜单评测 | ✅ C-Eval / CMMLU 等 | ❌ |
| 工具调用评估 | ❌ | ✅ 智能体工具调用评估器 |
| 格式校验 | ❌ | ✅ 格式校验评估器 |
| 从历史标注自动生成评估规则 | ❌ | ✅ 基于评测任务创建评估器 |

## 典型场景与选型建议

### 选择模型评测的场景

| 场景 | 说明 |
|------|------|
| **模型选型对比** | 需要在多个候选模型间快速对比基础能力（如理解力、生成质量、数学推理等） |
| **微调效果验证** | 完成 [[model-fine-tuning]] 后，需要量化验证调优是否提升了目标能力 |
| **通用能力回归** | 微调后需确认模型在 C-Eval 等基线榜单上的通用能力未退化 |
| **安全风险筛查** | 评估模型在政治敏感、违法犯罪、歧视偏见等维度的安全表现 |
| **Function Calling 精准度** | 通过字符串匹配规则验证模型的工具调用输出格式是否符合预期 |

### 选择应用评测的场景

| 场景 | 说明 |
|------|------|
| **端到端应用质量评估** | 评估包含 Prompt、知识库、插件等完整链路的应用输出效果 |
| **知识库 RAG 效果验证** | 需要归因分析（检索、重排、切片等环节）定位问题根因 |
| **多应用横向对比** | 对比不同 Prompt 策略或不同知识库配置下的应用表现 |
| **工作流输出验证** | 评估工作流应用的多步骤输出是否符合预期 |
| **持续质量监控** | 结合 [[application-observation]] 建立上线后的持续评测机制 |
| **复杂标注需求** | 需要多种标签类型（分类/布尔/数字/文本）进行细粒度人工标注 |

### 组合使用建议

对于完整的 AI 应用开发流程，建议将两套评估体系串联使用：

```
模型评测（选型 + 基线验证）
    ↓
模型微调 → 模型评测（调优验证 + 回归测试）
    ↓
应用构建（Prompt + 知识库 + 插件）
    ↓
应用评测（端到端质量评估 + 归因分析）
    ↓
上线运营 → 应用评测（持续监控 + 优化闭环）
```

## 决策流程图

开发者可按以下逻辑快速判断：

- **你在评估的是模型本身的能力吗？** → 使用 [[model-evaluation-introduction]]
- **你在评估的是一个已构建好的应用的输出效果吗？** → 使用 [[application-evaluation]]
- **你需要基线榜单回归测试吗？** → 使用 [[model-evaluation-introduction]] 的基线评测
- **你需要归因分析定位 RAG 链路问题吗？** → 使用 [[application-evaluation]] 的自动评测（旧版）
- **你需要自定义 Python 评分脚本吗？** → 使用 [[application-evaluation]] 的 Code 评估器（新版）
