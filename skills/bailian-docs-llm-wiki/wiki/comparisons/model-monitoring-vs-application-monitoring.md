# 模型监控与应用监控对比

## 概述

阿里云百炼平台提供两套互补的可观测能力：**模型监控**和**应用监控（应用观测）**。模型监控聚焦于模型调用层面的性能指标、Token 消耗和用量管理；应用监控则聚焦于应用内部的调用链路追踪和端到端可观测。开发者在技术选型时需要根据观测目标的不同，选择合适的监控方案，或组合使用两者以实现全方位的可观测覆盖。

## 关键维度对比

| 对比维度 | 模型监控 | 应用监控（应用观测） |
|----------|----------|----------------------|
| **监控粒度** | 模型调用级别（单次 API 请求） | 应用调用链路级别（Trace / Span） |
| **观测对象** | 所有通过 API 调用的模型（含自定义调优模型） | 智能体应用、工作流应用、高代码应用 |
| **核心指标** | Token 消耗、调用时长、首 Token 延时、RPM、TPM、失败率、内容安全错误 | 调用次数、失败率、Token 总量（输入/输出）、平均首 Token 耗时、平均调用时长 |
| **链路追踪** | 不支持（仅记录单次调用的输入/输出） | 支持完整调用链路追踪，含 CHAIN、AGENT、LLM、RETRIEVER、TOOL 等节点 |
| **日志能力** | 支持推理日志（需开通审计日志+推理日志，仅部分地域/模型） | 自动追踪所有 Prompt 输入及响应数据 |
| **数据筛选** | 按 API-KEY、推理类型、时间范围、模型筛选 | 按 Request ID、Trace ID、Span ID、状态、延时、Token 量、标签等组合筛选 |
| **告警能力** | 支持（短信、邮件、电话、钉钉、企业微信、Webhook） | 不支持 |
| **API 接口** | 支持 Prometheus HTTP API，可接入 Grafana 等工具 | 暂无 API 接口 |
| **数据导出** | 通过 Prometheus API 获取指标数据 | 支持导出为 JSONL 或 EXCEL 格式 |
| **数据标注** | 不支持 | 支持自定义标签标注（布尔值、分类、数字、文本） |
| **评测集集成** | 不支持 | 支持将 Span 数据批量添加到评测集 |
| **数据更新延迟** | 普通监控：小时级；高级监控：分钟级 | 分钟级 |
| **数据保留** | 用量统计保留最近 30 天 | 依赖可观测链路 OpenTelemetry 服务存储策略 |
| **支持地域** | 普通监控：全地域；高级监控：北京、新加坡、弗吉尼亚；告警：北京、新加坡 | 未明确地域限制（依赖 OpenTelemetry 服务开通） |
| **计费方式** | 模型监控功能本身不额外收费，模型调用按各模型定价计费 | 应用观测功能本身不收费，数据存储需支付可观测链路 OpenTelemetry 服务的存储费用 |
| **技术基础** | 私有 Prometheus 实例 | 可观测链路 OpenTelemetry 服务 |
| **开通方式** | 在模型监控配置中开启高级监控/审计日志/推理日志 | 需授权 OpenTelemetry 服务角色权限、开通服务并初始化存储 |

## 适用场景建议

### 模型监控适用场景

- **成本管控**：需要按模型、按业务空间追踪 Token 消耗和调用费用，设置用量告警防止超支。
- **SLA 保障**：关注模型响应延迟、首 Token 延时、失败率等性能指标，需对异常情况主动告警。
- **运维大盘**：需要将监控数据接入 Grafana 等第三方可视化工具，构建统一运维仪表盘。
- **直接 API 调用**：应用直接通过 API 调用模型，不使用百炼平台的智能体或工作流能力。
- **批量推理监控**：需要区分实时推理与批量推理的用量和性能指标。
- **免费额度管理**：需要监控免费额度消耗情况，并配置用完即停策略。

### 应用监控适用场景

- **应用调试**：在开发阶段需要追踪智能体或工作流内部的完整调用链路，定位各节点的耗时和异常。
- **RAG 链路分析**：需要观测检索（RETRIEVER）、向量化（EMBEDDING）、重排（RERANKER）等 RAG 相关节点的执行情况。
- **插件调用追踪**：需要了解智能体中各插件（TOOL 节点）的调用顺序、输入输出和耗时。
- **质量评估**：需要对模型输出进行数据标注，并将观测数据导入评测集进行效果评估。
- **问题排查**：通过 Trace ID 或 Request ID 快速定位某次调用失败的具体环节。
- **工作流优化**：分析工作流中各节点（API、分类器、条件分支等）的执行路径和性能瓶颈。

### 组合使用建议

| 场景 | 推荐方案 |
|------|----------|
| 仅通过 API 直接调用模型 | 模型监控 |
| 使用百炼智能体/工作流应用 | 应用监控 + 模型监控 |
| 需要主动告警和自动化运维 | 模型监控（应用监控暂不支持告警） |
| 需要 Grafana 集成 | 模型监控（通过 Prometheus API） |
| 需要调用链路追踪和节点级分析 | 应用监控 |
| 需要数据标注和评测 | 应用监控 |
| 全面可观测覆盖 | 两者同时启用 |

## 技术选型参考

### 选型决策流程

1. **确定观测目标**：如果关注的是模型级别的性能和成本，选择模型监控；如果关注的是应用内部链路和节点行为，选择应用监控。
2. **确认应用类型**：通过 Assistant API 创建的智能体不支持应用观测，此时只能依赖模型监控。高代码应用虽支持应用观测，但仅记录触发记录，内部链路需代码中主动上报。
3. **评估集成需求**：如需接入 Grafana 或自建监控系统，模型监控提供标准 Prometheus API；应用监控目前无 API 输出，适合在控制台内使用。
4. **考虑地域限制**：模型监控的高级功能（告警、日志）存在地域限制；应用监控依赖 OpenTelemetry 服务的可用性。
5. **规划告警策略**：目前仅模型监控支持告警配置，如需对应用层面的异常进行告警，需通过模型监控的指标间接实现。

### 注意事项

- 两套监控系统相互独立，数据不互通，但可通过 Request ID 关联同一次调用在两个系统中的记录。
- 模型监控侧重「量」的统计（调用量、Token 量、费用），应用监控侧重「质」的追踪（链路、节点、上下文）。
- 生产环境建议同时开启两者：用模型监控管控成本和设置告警，用应用监控排查问题和优化链路。
- 应用监控的数据存储会产生 OpenTelemetry 服务费用，建议评估数据量后再决定是否长期开启。
